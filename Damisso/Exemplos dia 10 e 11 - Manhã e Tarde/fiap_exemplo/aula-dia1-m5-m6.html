Conceito 1 de 13

2 — HTTP é uma conversa

HTTP = o protocolo da conversa na Web. Como no balcão: o cidadão pergunta, o atendente responde. Sempre os dois.

Request (pedido)

O que o Execute mandou: método + URL + (às vezes) body.

Response (resposta)

O que voltou: status + JSON (ou vazio no 204).

Regra

Não existe pergunta sozinha.

Cada Request espera uma Response.

Método · URL · Headers · Body · Status

O pedido tem 4 partes

1. Método

O que quero fazer: ler, criar, trocar, apagar.

GET · POST · PUT · PATCH · DELETE

2. URL

De quem estou falando.

/api/contribuintes/10

3. Headers

Etiquetas do envelope.

Ex.: “vou mandar JSON”.

4. Body

A carta — só quando há dados.

POST e PUT levam. GET quase nunca.

No balcão

Método — o gesto (consultar / cadastrar).

URL — a janela (contribuintes ou pedidos).

Body — o formulário preenchido.

Os próximos slides abrem cada verbo.

GET — só ler

No balcão: “mostra os contribuintes. Não mexe em nada.”

GET /api/contribuintes

A lista toda. Sem id na URL.

GET /api/contribuintes/10

Uma ficha. Se o 10 não existe → 404.

Lembre

GET não leva body.

É consulta — como pedir a ficha no arquivo.

Pode repetir mil vezes: o cadastro não muda.

POST — criar

No balcão: “quero cadastrar a Ana. NUIT 123456789.”

Body

O papel do cadastro: nuit, nome. Sem body não tem o que gravar.

Dois POST

Duas fichas. POST cria. Não atualiza a mesma pessoa.

Resposta

201 — criei, aqui está o id.

400 — NUIT inválido ou nome vazio.

POST /api/contribuintes

PUT — trocar a ficha inteira

A Ana mudou nome e data. Você manda a ficha completa de novo.

Foto nova

O que não mandar some ou fica vazio.

Id na URL

PUT /api/contribuintes/10 — quem atualizar.

PUT × PATCH

PUT = ficha inteira.

PATCH = um recorte (próximo slide).

Id inexistente → 404.

PATCH — mudar só um pedaço

Muda só o estado: ativo → inativo. Nome e NUIT ficam.

No INSS

Inativar contribuinte sem reescrever a ficha toda.

Body pequeno

Só o campo que muda. Ex.: { "status": "Inativo" }

Quando usar

PUT — correção completa da ficha.

PATCH — um detalhe (status).

DELETE — apagar

No INSS real quase não se apaga ficha. Aqui o DELETE serve para praticar o verbo.

Sem body

O id já vai na URL. Não manda JSON.

204

Deu certo e não vem corpo. O Swagger fica “vazio” — está ok.

404

O id 10 não existia. Não tinha o que apagar.

No Swagger

  1. DELETE /api/contribuintes/{id}
  2. Try it out · id = 10
  3. Execute
  4. Olhe o código: 204 ou 404

Depois um GET na lista: a Ana não aparece mais.

URL — de quem estamos falando

Em REST, recurso é o que a API expõe: a lista ou a ficha (contribuinte, pedido). A URL aponta para isso.

Coleção

Sem id: a lista toda. GET ou POST.

Um item

O 10 não é página 10. É o id da ficha.

Outro balcão

Pedidos de benefício: /api/pedidos.

Lembre

Mesma URL + verbo diferente = ação diferente.

GET …/10 lê. PUT …/10 troca. DELETE …/10 apaga.

Headers e Body

GET e DELETE quase não levam body. POST, PUT e PATCH levam JSON.

Header

Etiqueta no envelope. Ex.: Content-Type: application/json.

Body

A carta. Só quando há dados para enviar (cadastro, correção).

No Swagger

O body aparece na caixa preta quando o verbo precisa dele.

GET / DELETE: a caixa some — está certo.

3 — API

API = contrato do posto: “se perguntar assim, respondemos assim.” Swagger, app ou React usam a mesma API.

Cliente

Quem pergunta: Swagger, app, outro sistema.

Contrato

Rotas + verbos HTTP + formato JSON combinados.

Servidor

A InssApi processa e responde.

Por isso

Muda quem pergunta. O balcão (as rotas) é o mesmo.

Hoje o cliente é o Swagger. Depois pode ser o React.

4 — Input e Output

O cliente manda o input (Request). A API processa. Devolve o output (Response).

Cadastrar a Ana
Input: { "nuit": "123456789", "nome": "Ana Mucavel" } Output (já com id): { "id": 10, "nuit": "123456789", "nome": "Ana Mucavel" }

O fluxo

  1. Request carrega o input
  2. A API processa (valida, grava)
  3. Response entrega o output

O id nasce no servidor. O cliente não inventa.

5 — O que é REST

REST é o jeito padrão de organizar a API: cada ficha ou lista tem um endereço; o verbo HTTP diz o que fazer.

1. Recurso

O que a API expõe: lista de contribuintes, uma ficha, um pedido.

2. URL + método

URL = qual recurso. Método = o que fazer (GET, POST, PUT…).

3. Pedido completo

Cada request traz tudo o que precisa. A API não “lembra” o passo anterior.

Como escrevemos

/criarContribuinte — não.

POST /api/contribuintes — sim.

No Portal: Contribuinte · PedidoBeneficio

REST no Portal — exemplos

Mesma ideia dos verbos HTTP. Agora com o nome REST: substantivo na URL, verbo no método.

GET /api/contribuintes

Lista todos

GET …/10

Uma ficha (id 10)

POST /api/contribuintes

Cria (com body)

PUT …/10

Troca a ficha toda

PATCH …/10

Muda um pedaço

DELETE …/10

Apaga

Atenção

Não usem /criarContribuinte.

Usem POST /api/contribuintes.

6 — Endpoint

Endpoint = uma “janela” do balcão: método HTTP + rota (+ body, se precisar).

GET /api/contribuintes/10
↑ método     ↑ rota + parâmetro {id}

Método

GET, POST, PUT…

Rota

O endereço + {id}

Resposta

JSON + status

Tem sempre

Parâmetros · request · response · status.

Cada endpoint é uma janela do balcão.

7 — Controller

O balcão dos contribuintes: recebe o pedido HTTP e devolve JSON.

Controllers/ContribuintesController.cs
using Microsoft.AspNetCore.Mvc; namespace InssApi.Controllers; [ApiController] [Route("api/[controller]")] public class ContribuintesController : ControllerBase { }

Três papéis

  1. Recebe — o pedido HTTP
  2. Processa — valida e decide
  3. Devolve — status + JSON

Um controller por recurso.

8 — Route

Route = o endereço na porta do balcão. Diz qual URL cai em qual método.

// Controllers/ContribuintesController.cs
[Route("api/[controller]")]
[HttpGet("{id:int}")]
public IActionResult GetById(int id) { ... }

// vira: GET /api/contribuintes/10

Base

[Route] — api/contribuintes

Parâmetro

{id} — o 10 da URL

Nome

Tira “Controller” do nome da classe.

Como lê

ContribuintesController → contribuintes.

O {id} cai no argumento do método.

9 — Action

Action = o método C# que roda quando aquele pedido chega. Ex.: GET → Get() → Ok(lista).

Controllers/ContribuintesController.cs
private static readonly List<Contribuinte> _store = new(); [HttpGet] public IActionResult Get() { return Ok(_store); }

Três tempos

Recebe o pedido.

Executa (lista, valida, grava).

Retorna 200 / 201 / 400…

10 — DTO

DTO = Data Transfer Object: o formulário que atravessa o balcão (só o que o cliente manda ou recebe).

Models/CriarContribuinteRequest.cs
namespace InssApi.Models; public class CriarContribuinteRequest { public string Nuit { get; set; } = string.Empty; public string Nome { get; set; } = string.Empty; }

Por que existe

Transporta só o que o cliente pode ver/mandar.

Protege o objeto interno (id, status, regras).

No POST: o body JSON vira este DTO.

11 — Serialização

Serialização = traduzir C# ↔ JSON. O ASP.NET faz sozinho — vocês não montam o JSON na mão.

C#JSON
Nome = "Ana""nome": "Ana"
Nuit = "123456789""nuit": "123456789"

Serializar

Objeto → JSON (na Response)

Desserializar

JSON → objeto (no Request)

Vocês não fazem

Não montam string JSON à mão.

return Ok(c) já vira JSON.

12 — Validação

Validação = o porteiro do balcão. Formulário incompleto? Volta 400. Válido? Segue e grava.

NUIT

9 dígitos. Senão 400.

Nome

Vazio também volta 400. A API não inventa dado.

Antes de gravar

Toda entrada passa por validação.

Inválido = 400 na hora. Não processa.

13 — A resposta não é só o JSON

Uma API devolve três pedaços. Olhem o status primeiro — depois o JSON.

HTTP/1.1 201 Created
Content-Type: application/json { "id": 10, "nuit": "123456789", "nome": "Ana Mucavel" }

Três pedaços

Status — 201 = criei.

Headers — Content-Type JSON.

Body — a ficha (ou vazio no 204).

Status — sucesso

Olhe o número no Swagger antes do JSON.

200

“Aqui está.” GET, PUT, PATCH.

201

“Criei.” POST. Vem a ficha nova, já com id.

204

“Apaguei.” DELETE. Sem body. Está tudo bem.

Atalho

GET → 200

POST → 201

DELETE → 204

Status — o cliente errou

400

JSON incompleto ou NUIT inválido. Não gravamos.

404

Pediu o contribuinte 99 e ele não existe.

500

Quebrou do nosso lado (null, banco…). Não é o cidadão.

No Swagger

400 — leia a mensagem.

404 — o id está errado.

500 — olhe o código.

Os dois

RAM é rápida e volátil.

SQLite é um arquivo: inss.db.

Hoje o caderno é o arquivo na pasta do projeto.

1 — DbContext

DbContext = a sessão da API com o banco. Como abrir o arquivo do posto: fichas + pedidos.

Data/AppDbContext.cs
using Microsoft.EntityFrameworkCore; using InssApi.Models; namespace InssApi.Data; public class AppDbContext : DbContext { public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { } public DbSet<Contribuinte> Contribuintes => Set<Contribuinte>(); public DbSet<PedidoBeneficio> Pedidos => Set<PedidoBeneficio>(); }

O que ele faz

Agrupa as tabelas (DbSets).

Rastreia o que mudou até o SaveChanges.

Arquivo: Data/AppDbContext.cs

2 — DbSet<T>

DbSet = uma gaveta do caderno (uma tabela). Só busca quando alguém pergunta.

Não carrega tudo

Só busca quando você pede: ToListAsync().

Porta da tabela

Add, Find, Remove passam por aqui.

Na prática

_db.Contribuintes = a gaveta das fichas.

_db.Pedidos = a gaveta dos pedidos.

3 — Fluent API

Fluent API = regras da tabela fora da classe: chave, tamanho, único.

// Data/AppDbContext.cs — OnModelCreating
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Contribuinte>(e =>
    {
        e.HasKey(c => c.Id);
        e.Property(c => c.Nome).HasMaxLength(100);
        e.HasIndex(c => c.Nuit).IsUnique();
    });
}

Onde

No OnModelCreating.

Chave = Id · Nome ≤ 100 · NUIT único.

A classe Contribuinte fica limpa.

4 — Migration

Migration = receita que cria/atualiza as tabelas. C# muda → add → update → tabela no inss.db.

dotnet ef migrations add InitialCreate
dotnet ef database update

Dois passos

add — gera o C# da mudança.

update — aplica no arquivo inss.db.

Sem update, a tabela não existe.

5 — Connection string

Connection string = onde está o banco. No SQLite = um arquivo. Sem host, porta ou senha.

// appsettings.json
{
  "ConnectionStrings": {
    "Default": "Data Source=inss.db"
  }
}
// Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlite(
        builder.Configuration.GetConnectionString("Default")));

Onde

Arquivo: appsettings.json

Depois do update, nasce o inss.db na pasta do projeto.

6 — SaveChanges()

Add / Update / Remove só anotam. SaveChanges() é o carimbo — grava de verdade no arquivo.

Lápis

Add, Update, Remove — o EF só anota.

Tinta

SaveChanges() — agora grava no arquivo.

Atenção

Nada vai para o banco antes desse momento.

Esquecer o SaveChanges = a Ana some no F5 de novo.
