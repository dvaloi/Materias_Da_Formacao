O que é um GUID?

Identificador único — a “chave” da pessoa entre os dois mundos.

e5f6a7b8-1111-2222-3333-444455556666
  • Em Contribuintes → coluna Id
  • Em PedidosBeneficio → coluna ContribuinteId
  • Mesmo valor = mesma pessoa · sem copiar Nome/NUIT no pedido

Isto NÃO é “falta”

É a arquitetura que escolhemos — 2 bounded contexts.

  • ❌ Um único banco com as duas tabelas — monólito de dados; quisemos bancos independentes
  • ❌ JOIN SQL entre os dois databases — bancos diferentes; ponte = GUID na app

Isto NÃO é “falta” (2)

  • ❌ Coluna Nome em PedidosBeneficio — evita duplicar cadastro; nome só em Contribuintes
  • ❌ As duas APIs se chamando para gravar o pedido — cada microsserviço grava só no seu banco
Bounded context (DDD, padrão atual): cada contexto = regras + API + dados próprios.

Por que não tem JOIN?

  1. JOIN é para o mesmo banco. Aqui são dois: inss_contribuintes e inss_beneficios.
  2. Foi escolha. Não esquecemos a FK. Pessoa ≠ pedido de benefício.
  3. Bounded context: um módulo não amarra o outro num banco único.
  4. Ligação = GUID. Portal/APIs montam a tela — não o SQL.

Por que isso vale a pena

  • Independência
    :5001 ok com :5002 parado (e o contrário)
  • Clareza
    Cadastro num lugar · pedido noutro
  • Menos acoplamento
    Cada API dona do seu dado
  • Escala / deploy
    Publicar um contexto sem derrubar o outro
Padrão de mercado: microsserviços + bounded contexts

Para lembrar

Não tem JOIN porque são 2 contextos / 2 bancos.

A ponte é o ContribuinteId (GUID) —
independência, clareza e menos acoplamento.
