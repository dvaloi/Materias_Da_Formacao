Parte 2b — Testar o banco na máquina (passo a passo)

Regra de ouro — API NÃO precisa estar no ar
Depois que a Migration + seed já rodaram uma vez (API :5001 e :5002 subiram pelo menos uma vez), os dados ficam no volume do Docker. Vocês podem:
  • Parar as APIs (:5001 / :5002) e o portal (:5173)
  • Deixar só o Docker Desktop + container inss-postgres ligados
  • Consultar os dois bancos com docker exec / psql (ou DBeaver)
Consultar o banco ≠ chamar a API. O Postgres vive no container; a API só escreve/lê nele quando está ligada.
Antes de começar esta parte
  1. Docker Desktop aberto e verde.
  2. Na pasta projeto\api: docker compose up -d · docker ps mostra inss-postgres.
  3. Primeira carga (só se ainda não fizeram): subir :5001 e :5002 uma vez → Migration cria tabelas + seed. Depois podem parar as APIs (Ctrl+C nos PowerShells).
  4. Se a primeira carga já foi feita (ex.: aula anterior): não precisa subir API de novo — só o container no ar.
  5. Nesta parte as APIs podem estar paradas. Só o Docker importa.
Dois bancos, um container — vejam os dois
Container: inss-postgres · porta 5432
Banco 1 inss_contribuintes → tabela Contribuintes (API :5001)
Banco 2 inss_beneficios → tabela PedidosBeneficio (API :5002)
Relação: pedido guarda só ContribuinteId (GUID). Sem JOIN entre bancos.
Objetivo: listar tabelas e dados nos dois databases com a API desligada.

Como os dois bancos se relacionam (GUID)

Ideia em uma frase
O pedido não copia o nome nem o NUIT do contribuinte. Ele guarda só um GUID (= ContribuinteId) que é o mesmo valor do Id na tabela Contribuintes do outro banco.
O que é um GUID?
Um identificador único, tipo: 
e5f6a7b8-1111-2222-3333-444455556666
No nosso projeto:
  • Em Contribuintes, a coluna Id é o GUID da pessoa.
  • Em PedidosBeneficio, a coluna ContribuinteId guarda esse mesmo GUID.
  • Não existe FK (chave estrangeira) entre os dois bancos — o Postgres não faz JOIN automático.
  • Quem “liga” os dois é a aplicação (React + APIs), usando o GUID como ponte.

Leitura do diagrama (resumo)

Para lembrar (depois dos slides)
Não tem JOIN porque são 2 contextos / 2 bancos. A ponte é o ContribuinteId (GUID) — independência, clareza e menos acoplamento.
  • ❌ Não é monólito de um banco só · ❌ Não é JOIN entre databases · ❌ Pedido não copia Nome · ❌ APIs não se chamam para gravar
  • ✅ Bounded context (DDD) · ✅ cada API dona do seu dado · ✅ :5001 e :5002 independentes
