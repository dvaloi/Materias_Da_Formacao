Contexto — Por que modernizar?

O INSS Moçambique gerencia contribuintes e benefícios em Metical (MZN).

O sistema antigo é um legado MVC: difícil de testar, escalar e evoluir. Nestes dois dias vamos entender e praticar a versão moderna.

Antes — Legado

  • Monolito — tudo num só projeto
  • Controller com regra de negócio
  • Tela acoplada ao servidor
  • Testar e publicar: “tudo ou nada”

Agora — Moderno

  • Microsserviços (APIs independentes)
  • Portal React separado
  • Camadas DDD testáveis
  • CI/CD e deploys por serviço
Lembrete: o comparativo legado fica nestes slides. No Visual Studio vocês abrem só o sistema moderno.

Legado × Moderno — no código

A diferença não é só “pasta nova”. É onde mora a regra de negócio.

Legado — regra no controller

// Tudo misturado na tela/servidor public IActionResult Index() { foreach (var c in lista) c.Contribuicao = c.Salario * 0.03m; return View(lista); }

Moderno — regra no Domain

// Contribuinte.cs — testável e reutilizável public decimal CalcularContribuicaoMensal() { return Math.Round(SalarioMensal * 0.03m, 2); } // A API só orquestra — não calcula “na mão”
Na prática: abrimos Contribuinte.cs e o controller fino. Vocês vão ver a mesma ideia no React (validar no form) e no Domain (proteger de verdade).

Arquitetura — o mapa do projeto

Um portal. Duas APIs. Dois bancos.

↓
Postgresinss_contribuintes
API Benefícios:5002

O React não acessa o banco. As APIs não se chamam entre si — só o front fala com as duas.

Frase: “Um portal, dois departamentos, dois bancos.”

DDD — o negócio no centro

DDD = Domain-Driven Design (design dirigido pelo domínio).

É uma forma de organizar o código em torno do negócio, não da tecnologia. No INSS, o domínio é: NUIT, contribuição em MZN, pedidos de benefício.

API — HTTP fino
↓
Application — orquestra
↓
Domain — regras do negócioNuit · Contribuinte · Pedido
↓
Infrastructure — EF Core / Postgres
Em uma frase: a regra mora no Domain; a API só recebe e responde. Contribuintes ≠ Benefícios = dois bounded contexts (dois bancos).

SOLID — em uma frase cada

Princípios para código que cresce sem virar “spaghetti”.

S
Single Responsibility

Uma razão para mudar

O
Open/Closed

Estende sem quebrar o que já funciona

L
Liskov

Subtipos substituíveis

I
Interface Segregation

Interfaces pequenas e específicas

D
Dependency Inversion

Depende de abstração, não do EF Core

No INSS: Service de contribuinte não autentica; Auth não calcula contribuição. Service depende de IContribuinteRepository — por isso dá para testar com Moq (Dia 2).

Clean Code

Princípios aplicados

  • Nomes claros (CriarAsync, ObterPorNuit)
  • Funções pequenas e focadas
  • Validação no Domain (NUIT, salário MZN)
  • Controllers finos — delegam ao Service
  • DomainException com mensagens claras
// ❌ Legado — tudo no Controller if (nuit.Length != 9) { ViewBag.Erro = "..."; } contribuicao = salario * 0.03m; // ✅ Moderno — Domain encapsula regras var nuit = Nuit.Criar(request.Nuit); var c = Contribuinte.Criar(nuit, ...); var valor = c.CalcularContribuicaoMensal();

Microsserviços — como no INSS real

Um portal · dois departamentos · dois bancos

Não é assim

  • Uma API só para tudo
  • Um banco com tudo misturado
  • API chamando outra API

É assim (nosso projeto)

  • Contribuintes :5001 + Benefícios :5002
  • Bancos inss_contribuintes e inss_beneficios
  • React chama as duas; elas não se ligam

Pedido de benefício guarda só o contribuinteId — referência por ID, sem compartilhar tabela.

Repitam comigo: “Um portal, dois departamentos, dois bancos.”

O que a aplicação faz

Portal INSS Moçambique — cadastro de contribuintes e pedidos de benefício

  • Operador faz login e vê a lista de contribuintes (NUIT, salário em MZN, contribuição 3%)
  • Pode registrar contribuinte, abrir detalhe e criar pedido (reforma, pensão…)
  • 1 React → 2 APIs → 2 bancos Postgres (não compartilham tabelas)
