M13 Formulário controlado

O que é?

No React, o valor do campo fica no estado do componente (useState), não “solto” só no HTML. Cada tecla atualiza o estado; a tela mostra o que o estado manda.

Para que serve

  • Controlar o que o usuário digitou
  • Validar antes de enviar
  • Mostrar mensagens de erro por campo
  • Habilitar/desabilitar o botão

No portal INSS

  • Cadastro de contribuinte
  • NUIT com 9 dígitos
  • Salário em Metical (MZN)
  • Pedido de benefício
// Ideia value={'{'}form.nuit{'}'} onChange={'{'}e => setForm(...e.target.value){'}'}

M13 Validação e mensagens

Validar = garantir que o dado faz sentido antes (e depois) de gravar.

No frontend (React)

  • Resposta rápida para o usuário
  • Ex.: NUIT sem 9 dígitos → mensagem vermelha
  • Evita chamar a API à toa

No backend (.NET / Domain)

  • A regra de negócio “de verdade”
  • Value Object Nuit
  • API responde 400 se inválido
Importante: validação no front melhora a experiência. Validação no servidor protege o sistema. Vocês vão implementar as duas.

M13 React Router

O que é? Biblioteca que troca de página sem recarregar o site inteiro (SPA).

/login→/contribuintes→/contribuintes/:id→/pedidos

Conceitos

  • Rota — URL ligada a uma tela
  • Parâmetro — :id do contribuinte
  • Navegação — Link / navigate
  • Layout — menu fixo + conteúdo

Para que serve

  • Organizar o portal em telas
  • Compartilhar link direto
  • Voltar/avançar do browser
  • Experiência de sistema (não site estático)

M13 Estados da interface

Toda tela que busca dados precisa destes quatro estados:

Loading

Aguarde… a API ainda não respondeu.

Erro

Falhou (rede, 500…). Mostre mensagem e opção de tentar de novo.

Vazio

Deu certo, mas não há registros. Não é erro.

Sucesso

Dados na tela, ou “salvo com sucesso”.

Na implementação: vocês vão tratar esses estados nas listas de contribuintes e pedidos.

M13 useEffect e a aba Network

Ao abrir uma lista (contribuintes ou pedidos), o React busca dados na API com useEffect.

O que acontece

  • A tela monta → useEffect roda → fetch na API
  • DevTools → Network mostra a requisição
  • 200 = sucesso (mesmo com lista vazia [])

Por que aparece 2× em dev?

O projeto usa React Strict Mode (main.jsx).

  • Em desenvolvimento, o React monta o componente duas vezes de propósito
  • Por isso /api/pedidos pode aparecer duas vezes no Network
  • Não é bug — em produção (npm run build) chama 1 vez só
Pedidos vazios? Normal na primeira vez: o seed cria contribuintes, não pedidos. Use + Novo Pedido para testar o microsserviço de Benefícios (:5002).

M14 Autenticação

Autenticação = provar quem você é. No portal usamos JWT.

1. Usuário
admin / 123 no React
2. React
POST /api/auth/login → API Contribuintes
3. API
devolve token JWT
4. React
guarda inss_token no localStorage
5. Depois
GET /api/… com Authorization: Bearer … → 200 ou 401
Login de teste: admin / 123. Token no localStorage · header Authorization: Bearer …

M14 Context API (estado global)

Estado global = informação compartilhada por várias telas (usuário logado, token).

O que é Context API

  • Recurso nativo do React
  • Evita passar props em toda a árvore
  • No projeto: AuthContext
  • Qualquer tela usa useAuth()

O que guardamos

  • Dados do usuário (nome)
  • Se está autenticado
  • Funções login / logout
  • Token no localStorage
Sessão: enquanto o token for válido, o usuário continua “dentro” do portal. No logout (ou 401), a sessão é limpa.

M14 Rotas protegidas

Rota protegida = só entra quem está autenticado.

Usuário abre /contribuintes→Tem token?→Sim: entra · Não: /login

No React

  • Componente ProtectedRoute
  • Melhora a experiência
  • Esconde telas internas

Na API (.NET)

  • Atributo [Authorize]
  • Segurança de verdade
  • Sem JWT → 401 Unauthorized
Front e API trabalham juntos: o React redireciona; a API bloqueia acesso indevido. Em 401, o portal limpa a sessão e volta ao login.

Responsividade

M15 Por que automatizar testes?

Teste automatizado = programa que verifica outro programa.

Exemplos de regras do INSS

  • NUIT tem 9 dígitos
  • Contribuição = 3% do salário
  • Pedido aprovado só se estiver pendente

Benefício

  • Detecta regressão cedo
  • Documenta o comportamento
  • Dá segurança para refatorar
  • Alimenta o pipeline (M16)

M15 Três níveis de teste

E2E — fluxo no navegador (Playwright)
Integração — API completa (WebApplicationFactory)
Unitário — regras isoladas (xUnit + Moq)

Unitário

Rápido, muitos. Testa Domain/Service sem UI.

Integração

HTTP real: login, JWT, endpoints.

E2E

Poucos. Simula o usuário na tela.

Equilíbrio: a maioria dos testes é unitária; e2e só nos fluxos críticos (ex.: login).

M15 AAA, xUnit, Moq e TDD

// Estrutura de todo teste unitário Arrange — prepara os dados Act — executa o método Assert — verifica o resultado

xUnit

Framework de testes .NET. Você escreve métodos com [Fact] e roda dotnet test.

Moq

Cria um “dublê” do repositório. Isola o Service sem precisar do banco.

TDD

Test-Driven Development: escrever o teste (vermelho) → código (verde) → melhorar.

M15 WebApplicationFactory e Playwright

WebApplicationFactory

O que é: ferramenta do ASP.NET que sobe a API em memória para testes.

  • Chama /api/... de verdade
  • Exercita Controllers + JWT
  • Usa o banco configurado (Postgres)

Playwright

O que é: automação de navegador.

  • Abre o Chrome/Chromium
  • Digita, clica, espera textos
  • Valida o fluxo ponta a ponta
Exemplo de escolha: regra dos 3% → teste unitário no Domain. Fluxo “login e ver lista” → candidato a e2e.

M16 Quality gates e artefatos

Quality gate

Regra de qualidade: o pipeline só passa se build e testes estiverem ok.

  • Verde → pode seguir
  • Vermelho → corrija antes de avançar

Artefatos

Arquivos gerados e guardados pelo pipeline.

  • Resultados de teste
  • Build do React (dist)
  • Servem para análise e publicação
Se um teste falha, vocês analisam o log do Actions: qual projeto falhou e qual Assert quebrou.
